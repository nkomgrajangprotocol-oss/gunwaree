# GunWaree (FloodSense)

ระบบต้นแบบเฝ้าดูระดับน้ำและแจ้งเตือนน้ำท่วมสำหรับกรุงเทพฯ และลุ่มน้ำเจ้าพระยา สร้างสำหรับ U-Hackathon 2026 (แทร็ก AI) โดยทีม KaNaIYuRi

> **ไม่ใช่ประกาศเตือนภัยทางการ** นี่คือระบบต้นแบบสำหรับงานแฮกกาธอน ข้อมูลมาจากแหล่งสาธารณะและอาจล่าช้า การแจ้งเหตุในระบบนี้ถึงเฉพาะผู้ดูแลของโครงการ ไม่ถูกส่งถึงหน่วยกู้ภัย หากเป็นเหตุฉุกเฉินจริง โทร 191 (เหตุฉุกเฉินทั่วไป) หรือ 1784 (กรมป้องกันและบรรเทาสาธารณภัย) เหตุเจ็บป่วยฉุกเฉินโทร 1669

**English TL;DR:** GunWaree is a hackathon prototype that collects public water, rain and road-flooding data, shows it on a web app, and gives a rule-based flood level for the Chao Phraya river at Ayutthaya (station 39). It also includes an ESP32 water-level test rig that reports to the same backend and can receive pump commands from an admin (the demo drives only a relay LED: no real pump is connected because one fail-safe test failed, see "Test status"). We tested machine-learning models against the simple rule, found that only 5 independent flood events exist in six years of data (too few to prove a model is better), and shipped the rule. It is not an official warning system.

## สิ่งที่ระบบทำ

**ผู้ใช้ทั่วไป (ไม่ต้อง login)**
- ดูระดับน้ำแม่น้ำและคลอง ฝน จุดวัดน้ำท่วมถนน ระดับรายเขต และเขื่อน ทุกค่ามีเวลาที่วัดกำกับ
- ดูระดับความเสี่ยงของสถานีพระนครศรีอยุธยา (คำนวณจากกฎง่ายๆ ดูหัวข้อ "ระดับความเสี่ยง")
- "สถานการณ์ใกล้คุณ": ขอตำแหน่งจากเบราว์เซอร์เมื่อกดปุ่ม แล้วหาจุดวัดที่ใกล้ที่สุด ตำแหน่งอยู่ในเบราว์เซอร์เท่านั้น ไม่ถูกส่งหรือเก็บ
- กระดิ่งแจ้งเตือน (แสดงเฉพาะการแจ้งเตือนที่ผู้ดูแลอนุมัติส่งแล้ว)

**ผู้ใช้ที่สมัครและ login แล้ว**
- แจ้งเหตุ (คำอธิบาย ที่อยู่ เบอร์โทร และพิกัดถ้าปักหมุด) และดูรายการแจ้งเหตุของตัวเอง

**ผู้ดูแลระบบ (admin)**
- สร้างและอนุมัติการแจ้งเตือน (สร้างแล้วอยู่สถานะรอ ต้องกดส่งก่อนจึงขึ้นกระดิ่ง)
- ดูและเปลี่ยนสถานะรายการแจ้งเหตุ
- สั่งรีเลย์ของชุดทดลอง ESP32 (เดโมไม่ต่อปั๊มจริง) และดูสถานะรีเลย์
- ดูกราฟระดับน้ำที่อยุธยาย้อนหลัง 24 ชั่วโมง

**ชุดทดลอง ESP32 (ฮาร์ดแวร์)**
- วัดระดับน้ำในภาชนะด้วยเซนเซอร์อัลตราโซนิก ส่งค่าเข้า backend ผ่าน HTTPS
- ถามคำสั่งปั๊มจาก backend ทุก 5 วินาที สั่งรีเลย์เปิดได้ครั้งละไม่เกิน 60 วินาที ปิดทันทีเมื่อ Wi-Fi หลุด (ทดสอบแล้ว) แต่**ไม่ผ่านการทดสอบ**กรณีต่อ Wi-Fi อยู่แต่ไม่มีอินเทอร์เน็ต จึงยังไม่ต่อปั๊มจริง เดโมใช้ไฟ LED บนโมดูลรีเลย์แทนปั๊ม (ดู "สถานะการทดสอบ")

## สถาปัตยกรรม

```
แหล่งข้อมูลสาธารณะ ─────────► backend/fetch_latest.py ─► SQLite ─► FastAPI (23 endpoint) ─► หน้าเว็บ (HTML/CSS/JS)
 POPNIX Flood  (ระดับน้ำ ถนน ฝน)        ดึงตามรอบ + backfill ตอนเริ่ม   │
 Open-Meteo    (ฝน/อากาศ)                                                └──► ESP32 (POST ค่า, GET คำสั่งปั๊ม)
 กรมชลประทาน    (เขื่อน)
 ThaiWater/สสน. (ข้อมูลย้อนหลังสำหรับทดสอบกฎและโมเดล)
```

- หน้าเว็บไม่เรียกแหล่งข้อมูลภายนอกโดยตรง เรียกแต่ backend ของเรา
- ถ้าเรียก backend ไม่ได้ หน้าเว็บใช้ข้อมูลตัวอย่างจาก `frontend/sample/` พร้อมป้าย "ข้อมูลตัวอย่าง"
- สิทธิ์: guest / client / admin ตรวจที่ backend (token แบบ Bearer) อุปกรณ์ ESP32 ใช้ header `X-Device-Key`

## ระดับความเสี่ยง (ใช้กฎ ไม่ใช่โมเดล AI)

`GET /risk` ประเมินที่สถานีพระนครศรีอยุธยา (สถานี 39) ระดับตลิ่ง 5.06 ม. รทก. ใช้ margin `m = 0.30` ม. (ค่านี้เลือกจากข้อมูลย้อนหลัง 2020 ถึง 2024 ดูหัวข้อ "การทดสอบโมเดล")

| ระดับ | เงื่อนไข |
|---|---|
| วิกฤต (`critical`) | ระดับน้ำ ≥ 5.06 ม. |
| เตือนภัย (`warning`) | > 4.76 ม. และสูงขึ้นเมื่อเทียบกับ 6 ชั่วโมงก่อน |
| เฝ้าระวัง (`watch`) | > 4.76 ม. แต่ไม่ได้สูงขึ้น (หรือไม่มีค่าเทียบ) |
| ปกติ (`none`) | ≤ 4.76 ม. |

- `risk_percent` ที่ API ส่งมามีแค่ 0, 33, 67, 100 ตามระดับ ไม่ใช่ความน่าจะเป็น หน้าเว็บแสดงเป็นระดับ ไม่แสดงเป็นเปอร์เซ็นต์
- **ไม่ประเมินจากข้อมูลเก่า:** ถ้าค่าล่าสุดของสถานี 39 เก่ากว่า 3 ชั่วโมง `/risk` ตอบ 503 และหน้าเว็บบอกว่ายังไม่มีข้อมูลให้ประเมิน (เกิดขึ้นจริงเมื่อต้นทาง POPNIX ค้างข้อมูลแม่น้ำที่ 15 ต.ค. 23:10)
- **กันค่าเพี้ยน:** ถ้าค่าล่าสุดห่างจากมัธยฐานของค่าก่อนหน้า (สูงสุด 4 ค่าใน 6 ชั่วโมง) เกิน 1.0 ม. ระบบถือว่าน่าสงสัยและใช้มัธยฐานแทน จนกว่าจะมีค่าสูงยืนยันกัน 3 ค่า ข้อมูลย้อนหลังมีค่าเดี่ยวสูง 5 ถึง 7 ม. ซึ่งจะทำให้ขึ้นวิกฤตปลอมถ้าไม่กัน

## การทดสอบโมเดล และเหตุผลที่ไม่ใช้โมเดล

เราทดสอบว่าโมเดลเรียนรู้ (Machine Learning) ทายน้ำล้นตลิ่งที่อยุธยาใน 24 ชั่วโมงข้างหน้าได้ดีกว่ากฎหรือไม่ แล้ว**ตัดสินใจไม่ใช้โมเดลในระบบจริง** สรุปการทดลอง:

**ข้อมูล**
- ระดับน้ำอยุธยา (สถานี 39), นครสวรรค์ (568), การไหลที่ C.13 และ C.2 จาก ThaiWater รายชั่วโมง กับฝนจาก Open-Meteo ช่วง 2020 ถึง 2025 (ไฟล์อยู่ใน `data/` ซึ่งไม่ขึ้น GitHub)
- ตัดค่าเดี่ยวที่เพี้ยนด้วย rolling median (หน้าต่าง 70 นาที เกณฑ์ 1.0 ม.) วันที่ระดับน้ำสูงสุดเกินตลิ่งจึงเหลือ **76 วัน** เป็น **5 เหตุการณ์อิสระ** (2021: 1, 2022: 2, 2025: 2) ผลไม่เปลี่ยนเมื่อลองหน้าต่าง 5, 7, 9 และเกณฑ์ 0.5, 1.0, 2.0 เกณฑ์นี้เลือกหลังเห็นข้อมูลทั้งชุด แต่ใช้เกณฑ์เดียวกันทุกปีและไม่ได้ปรับตามผลโมเดล

**วิธีตรวจ**
- เหตุการณ์น้อยเกินไปสำหรับวิธีแบ่งตามปีทั่วไป จึงตรวจ 2 รอบ: ทดสอบปี 2021 (เทรนปีอื่นใน 2020 ถึง 2024) และปี 2022 ตัดชั่วโมงเทรนที่ใกล้ขอบปีทดสอบภายใน 72 ชั่วโมงเพื่อกัน label ปนกัน
- ปี 2025 ใช้ทดสอบครั้งเดียวหลังตัดสินใจแล้ว ไม่ได้ใช้ปรับอะไร

**ผล (F1 ระดับชั่วโมง เฉลี่ยสองรอบ)**

| วิธี | F1 |
|---|---|
| กฎ B2 (ที่ใช้งาน, `m = 0.30`) | 0.492 |
| กฎ B1 (ระดับ > ตลิ่ง − 0.05 ม.) | 0.928 |
| Logistic Regression (ตัวแปรน้อย) | 0.862 |
| Logistic Regression (ตัวแปรเต็ม) | 0.876 |
| HistGradientBoosting | 0.916 |

โมเดลทั้งสามชนะกฎ B2 ตามเกณฑ์ที่ตั้งไว้ล่วงหน้า แต่เราไม่ใช้ เพราะ

1. เกณฑ์ที่ตั้งไว้เทียบกับ B2 อ่อนเกินไป (B2 มีเงื่อนไข "กำลังขึ้น" ทำให้พลาดชั่วโมงที่น้ำเกินตลิ่งอยู่แล้ว F1 จึงต่ำ) กฎ B1 ซึ่งแทบแค่จับชั่วโมงที่เกินตลิ่ง ก็ชนะโมเดลทุกตัว นี่คือข้อผิดพลาดในการออกแบบเกณฑ์ของเราเอง
2. ในชั่วโมงที่น้ำยังต่ำกว่าตลิ่ง (งานจริงของการเตือน) กฎ B2 ได้ F1 เฉลี่ย 0.669 สูงกว่าโมเดล (0.555 และต่ำกว่า) โมเดลจับได้ครบแต่เตือนผิดมาก
3. โมเดลเรียนรู้ทางลัดจากเหตุการณ์ปี 2022 ที่ข้อมูลขาดเป็นช่วง ("ข้อมูลขาด = น้ำท่วม") ซึ่งไม่จริง
4. โมเดลใช้ตัวแปรการไหลและฝนที่ระบบสดยังไม่ดึง
5. เหตุการณ์ในชุดเทรนมีเพียง 3 ครั้ง

**ผลของกฎที่ใช้งานจริงบนปี 2025 (ข้อสอบอิสระมี 2 เหตุการณ์)**

lead time คือจำนวนชั่วโมงที่เตือนก่อนน้ำถึงตลิ่งครั้งแรก (บวก = เตือนก่อน ลบ = เตือนหลัง ค้นย้อนหลังได้ไม่เกิน 72 ชั่วโมง)

| เหตุการณ์ | กฎ ระดับเฝ้าระวังขึ้นไป | กฎ ระดับเตือนภัยขึ้นไป | HistGradientBoosting |
|---|---|---|---|
| 2025 ต.ค. 4 ถึง 6 | +71.3 | +66.3 | +54.3 |
| 2025 พ.ย. 5 ถึง 23 | +1.7 | −0.3 | +23.7 |
| 2021 ก.ย. 30 ถึง พ.ย. 1 | +36.0 | +36.0 | +72.0 |
| 2022 ก.ย. 30 ถึง ต.ค. 13 | +27.2 | +27.2 | +32.2 |
| 2022 ต.ค. 20 ถึง 28 | −0.5 | −0.5 | +23.5 |

- กฎเตือนทันก่อนน้ำถึงตลิ่ง 4 จาก 5 เหตุการณ์ที่ระดับเฝ้าระวังขึ้นไป และ 3 จาก 5 ที่ระดับเตือนภัยขึ้นไป ที่ไม่ทันคือกรณีน้ำขึ้นจากต่ำกว่าเกณฑ์ถึงตลิ่งภายในไม่กี่ชั่วโมง กฎเกณฑ์คงที่ตามไม่ทัน
- ปี 2021 และ 2022 ดูดีเกินจริง เพราะค่า `m` เลือกจากสองปีนี้
- เตือนผิด (ระดับเตือนภัยขึ้นไป แต่ไม่ถึงตลิ่งใน 24 ชั่วโมง) ปี 2025 มี 9 วัน (ราว 0.75 วันต่อเดือน) ส่วนหนึ่งเป็นการเตือนล่วงหน้าเกิน 24 ชั่วโมงก่อนเหตุการณ์ ไม่มีการเตือนผิดนอกฤดูน้ำหลาก
- โมเดลเตือนก่อนครบทั้ง 5 เหตุการณ์ แต่ด้วยเหตุการณ์เพียง 5 ครั้ง เราสรุปไม่ได้ว่าโมเดลดีกว่ากฎ
- ตัวเลขความแม่นรายชั่วโมงของปี 2025 ไม่ใช่ความแม่นของระบบ เพราะชั่วโมงในเหตุการณ์เดียวกันไม่เป็นอิสระต่อกัน

ระบบเก็บผลประเมินลงตาราง `predictions` พร้อมช่องผลจริง (`actual_outcome`) ไว้สะสมข้อมูลสำหรับรุ่นต่อไป

## สถานะการทดสอบ (ซื่อตรงว่าอะไรทดสอบแล้ว อะไรยัง)

| ส่วน | สถานะ |
|---|---|
| Backend | ทดสอบกรณีสิทธิ์และรหัสสถานะของทุก endpoint กับฐานข้อมูลชั่วคราว (91 กรณีผ่าน) และทดสอบบน Railway จริง |
| หน้าเว็บ | ทดสอบในเบราว์เซอร์กับ backend จริง (16 ต.ค.) ยังไม่ได้ทดสอบทุกเบราว์เซอร์หรืออุปกรณ์ |
| ESP32 → backend | ทดสอบแล้ว: ส่งค่า `POST /device/readings` สำเร็จ ค่าตรงกับที่ backend เห็น |
| ESP32 รีเลย์ (ไม่ต่อปั๊ม) | ทดสอบแล้ว: สั่งเปิดจาก admin ไฟรีเลย์ติดภายใน 1.7 วินาทีในรอบวัด ดับเองราว 1 นาที (ตัวจับเวลา 60 วินาที) ตอนบูตไม่ติด 8 จาก 8 ครั้ง (โมดูลเป็น active-HIGH) |
| ESP32 สั่งปิดกลางทาง | ทดสอบแล้ว: สั่งเปิดแล้วสั่งปิด ไฟดับภายใน 5 วินาที (ไม่ได้วัดละเอียด) |
| ESP32 fail-safe: Wi-Fi หลุด | ทดสอบแล้ว: ผ่าน ปิด hotspot ทั้งตัวขณะรีเลย์ติด ไฟดับราว 3 วินาที |
| **ESP32 fail-safe: ต่อ Wi-Fi อยู่แต่ไม่มีอินเทอร์เน็ต** | **ไม่ผ่าน:** ปิดข้อมูลมือถือขณะรีเลย์ติด (Wi-Fi ยังต่ออยู่) รีเลย์ไม่ดับภายใน 90 วินาที ทั้งที่ตัวจับเวลาตั้งไว้ 60 วินาที สมมติฐาน (ยังไม่ได้ยืนยัน): `loop()` ถูกการเรียก HTTPS ที่รอ timeout ค้างไว้ ตัวจับเวลาจึงไม่ถูกเช็กตรงเวลา เราจึงไม่ต่อปั๊มจริง |
| **ยังไม่ได้ทดสอบ** | ปั๊มจริง, วงจรฝั่งโหลด, ค่าเกณฑ์สีของเซนเซอร์ที่วัดจริง |

ค่าระดับน้ำของชุดทดลองที่เห็นบนเว็บอาจยังไม่ตรงน้ำจริง เพราะ `SENSOR_HEIGHT_CM`, `YELLOW_CM`, `RED_CM` ในโค้ดบอร์ดต้องตั้งตามภาชนะที่ใช้

**เดโมนี้ไม่ต่อปั๊มจริง** ใช้ไฟ LED บนโมดูลรีเลย์แสดงผลคำสั่งจาก admin แทน (admin สั่ง, บอร์ดรับคำสั่ง, รีเลย์ตอบสนอง) เหตุผลคือผลทดสอบ fail-safe ข้างบนยังไม่ผ่านครบ และปั๊มเกี่ยวข้องกับน้ำและไฟฟ้า

## วิธีใช้งานเว็บเดโม

1. เปิด https://gunwaree-frontend.vercel.app (ครั้งแรกจะมีกล่อง "นี่คือเว็บเดโม" กด "รับทราบ" เปิดดูซ้ำได้จากลิงก์ท้ายหน้า)
2. ดูข้อมูลได้ทันทีโดยไม่ต้อง login: ระดับน้ำ ถนน ฝน เขื่อน และระดับความเสี่ยง ป้าย "ไม่อัปเดต" หมายความว่าค่าเก่ากว่า 3 ชั่วโมง
3. กดปุ่ม "ดูสถานการณ์ใกล้คุณ" เพื่อหาจุดวัดที่ใกล้ที่สุด (อนุญาตตำแหน่งในเบราว์เซอร์ หรือเลือกเขตเอง)
4. กดกระดิ่งเพื่อดูการแจ้งเหตุที่ผู้ดูแลส่งแล้ว
5. สมัครบัญชี (รหัสผ่านอย่างน้อย 8 ตัว มีทั้งตัวอักษรและตัวเลข) เพื่อแจ้งเหตุ ข้อมูลที่ส่งเป็นข้อมูลทดสอบและผู้ดูแลเห็นได้

## วิธีรันบนเครื่องตัวเอง

ต้องมี Python 3.10 ขึ้นไป (ทดสอบกับ Python 3.13 บน Railway) และ VS Code พร้อม Live Server สำหรับหน้าเว็บ

### Backend

```bash
git clone https://github.com/nkomgrajangprotocol-oss/gunwaree.git
cd gunwaree
python3 -m venv venv
venv/bin/pip install -r backend/requirements.txt     # Windows: venv\Scripts\pip ...
cp .env.example .env                                  # แล้วแก้ค่าใน .env (ดูตารางด้านล่าง)
cd backend
../venv/bin/uvicorn main:app --reload                 # เปิด http://127.0.0.1:8000/docs
```

ตัวแปรสภาพแวดล้อม (ตั้งใน `.env` หรือในแพลตฟอร์ม deploy ห้ามใส่ค่าจริงลง repo)

| ตัวแปร | ใช้ทำอะไร |
|---|---|
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | บัญชีผู้ดูแลระบบ สร้างตอนเริ่มระบบ (ถ้าไม่ตั้ง จะข้ามการสร้าง) |
| `DEVICE_KEY` | รหัสที่อุปกรณ์ ESP32 ส่งใน header `X-Device-Key` (ถ้าไม่ตั้ง ระบบปฏิเสธทุกคำขอจากอุปกรณ์) |
| `DB_PATH` | ที่เก็บไฟล์ SQLite (ไม่บังคับ ดูค่าเริ่มต้นใน `backend/db.py`) บน Railway ชี้ไปที่ volume `/data` |

ตอนเริ่ม backend ดึงข้อมูลจากแหล่งสาธารณะและ backfill ย้อนหลังเอง ต้องมีอินเทอร์เน็ต ถ้าแหล่งใดล่ม ค่าของแหล่งนั้นจะว่างหรือเก่า

### หน้าเว็บ

หน้าเว็บเป็น HTML/CSS/JavaScript ล้วน ไม่มีขั้นตอน build:

1. เปิดโฟลเดอร์โปรเจกต์ใน VS Code คลิกขวาที่ `frontend/index.html` แล้วเลือก "Open with Live Server" (พอร์ต 5500)
2. ที่อยู่ backend ตั้งที่เดียวใน `frontend/js/api.js` (`GW.BASE_URL`) ค่าเริ่มต้นชี้ไป backend บน Railway
3. **ถ้ารัน backend เองในเครื่อง** ต้องแก้ `GW.BASE_URL` เป็น `http://127.0.0.1:8000` และเพิ่ม origin ของหน้าเว็บ (เช่น `http://127.0.0.1:5500`) ในรายการ `allow_origins` ของ CORS ใน `backend/main.py` ต้องตรงทุกตัวอักษร (`127.0.0.1` ไม่เท่ากับ `localhost`) backend บน Railway อนุญาตเฉพาะโดเมนเว็บเดโม จึงเปิดจาก Live Server แล้วเรียก backend สาธารณะไม่ได้

### Firmware (ESP32)

อุปกรณ์: ESP32 DevKit V1, เซนเซอร์ระยะแบบ TRIG/ECHO (โค้ดเขียนตามรุ่น HC-SR04 ซึ่งไม่กันน้ำ ต้องติดตั้งให้พ้นละอองน้ำ และขา ECHO ต้องผ่านตัวแบ่งแรงดันจาก 5V เป็น 3.3V), โมดูลรีเลย์, LED 3 ดวง

1. ติดตั้ง Arduino IDE และ ESP32 board package (ทดสอบกับ core 3.3.12) เลือกบอร์ด "ESP32 Dev Module"
2. ในโฟลเดอร์ `firmware/rig/` คัดลอก `secrets.example.h` เป็น `secrets.h` แล้วใส่ `WIFI_SSID`, `WIFI_PASS` (ต้องเป็น Wi-Fi 2.4 GHz ที่ออกอินเทอร์เน็ตได้) และ `DEVICE_KEY` (ต้องตรงกับค่าบน backend) `secrets.h` ไม่ขึ้น GitHub
3. ตั้งค่าที่หัว `rig.ino`: `SIMULATE_SENSOR` ต้องเป็น `0` สำหรับของจริง (1 ใช้ทดสอบโดยไม่มีเซนเซอร์เท่านั้น), `SENSOR_HEIGHT_CM` (ระยะจากหน้าเซนเซอร์ถึงก้นภาชนะ), `YELLOW_CM`, `RED_CM`, และ `RELAY_ACTIVE_LOW` (โมดูลของเราเป็น active-HIGH จึงตั้งเป็น `false` ให้ทดสอบโมดูลของคุณก่อน)
4. กด Verify และ Upload เปิด Serial Monitor ที่ 115200 ควรเห็น `POST -> 201` ทุก 10 วินาที (ทุก 3 วินาทีเมื่อสถานะเหลืองหรือแดง) แล้วตรวจที่ `GET /stations/latest?kind=canal&scope=bangkok_test` ว่าเห็น `esp32-01`
5. **ความปลอดภัยของปั๊ม:** ต่อฝั่งโหลดของรีเลย์ที่ขา `COM` กับ `NO` (ไม่ใช่ `NC`) ใช้ไฟเลี้ยงปั๊มแยกจาก ESP32 กราวด์ร่วมกัน ใส่ไดโอด flyback ถ้าเป็นโซลินอยด์ **firmware เวอร์ชันนี้ไม่ผ่านการทดสอบ fail-safe** กรณีต่อ Wi-Fi อยู่แต่ไม่มีอินเทอร์เน็ต (รีเลย์ไม่ดับภายใน 90 วินาที) **อย่าต่อปั๊มจริงจนกว่าจะแก้และทดสอบซ้ำ** ถอดโหลดแล้วดูแค่ไฟ LED บนโมดูลรีเลย์ ทางแก้ที่เราเสนอแต่ยังไม่ได้ทำ: แยกตัวป้องกันเวลาปั๊มเป็นงานแยก (FreeRTOS task) ที่ไม่เรียกเครือข่าย และลด timeout ของการเรียก HTTPS

### โมเดล (สคริปต์ทดลอง ไม่ถูกเรียกตอนรัน API)

`model/prepare_data.py` → `model/train.py` → `model/evaluate.py` (และ `model/guard_check.py`) ต้องมีไฟล์ข้อมูลใน `data/` (ระดับน้ำ 3 สถานี การไหล 2 สถานี ฝน 2 จุด ช่วง 2020 ถึง 2025) ซึ่ง**ไม่ได้อยู่ใน repo** และสคริปต์ดาวน์โหลดก็ไม่ได้อยู่ใน repo ด้วย การรันซ้ำจากศูนย์จึงทำไม่ได้ในตอนนี้ ผลการทดลองดูในหัวข้อ "การทดสอบโมเดล" ข้างบน

## วิธี deploy

**Backend บน Railway**
- Root Directory: `backend`
- Start Command: `uvicorn main:app --host 0.0.0.0 --port $PORT`
- ตั้งตัวแปร `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `DEVICE_KEY` ในหน้า Railway และผูก volume ที่ `/data` แล้วตั้ง `DB_PATH` เป็นไฟล์ในนั้น (ฐานข้อมูลจึงอยู่รอดเมื่อ deploy ใหม่)
- Railway build ใหม่ทุกครั้งที่ `main` เปลี่ยน เราใช้บัญชีทดลอง (เครดิตจำกัด)

**หน้าเว็บบน Vercel**
- Framework Preset: Other, Root Directory: `frontend`, ไม่มี build command (ไม่ต้องมี `vercel.json`)
- โดเมนหลักของโปรเจกต์ต้องอยู่ในรายการ CORS ของ backend เทียบตรงตัว ลิงก์ preview ของแต่ละ deployment ใช้เรียก backend ไม่ได้

## ข้อจำกัดและความปลอดภัยที่ทราบ

- ระบบนี้คือต้นแบบ ข้อมูลสาธารณะมีเวลาล่าช้าและอาจผิดพลาด ใช้ตัดสินใจเรื่องความปลอดภัยไม่ได้
- ระดับความเสี่ยงเป็นกฎที่สถานีเดียว ไม่ใช่การพยากรณ์น้ำท่วมของพื้นที่ใด และพลาดกรณีน้ำขึ้นเร็วมาก (ดูตารางผลปี 2025)
- ไม่มี rate limit ที่หน้า login
- ไม่มี logout ฝั่ง server: กดออกจากระบบจะลบ token ในเบราว์เซอร์ แต่ token ยังใช้ได้ที่ server ราว 24 ชั่วโมง
- การลืมรหัสผ่านเป็นโหมดจำลอง: ระบบไม่ส่งอีเมล รหัสรีเซ็ตถูกพิมพ์ในบันทึกของ server ซึ่งทีมงานเข้าถึงได้ (ในฐานข้อมูลเก็บเป็นค่าแฮช)
- fail-safe ของ ESP32 ยังมีช่องโหว่: ถ้าต่อ Wi-Fi อยู่แต่ไม่มีอินเทอร์เน็ต รีเลย์ไม่ดับตามเวลา 60 วินาทีที่ตั้งไว้ (ทดสอบแล้วไม่ผ่าน ดับไม่ทันภายใน 90 วินาที) เราจึงไม่ต่อปั๊มจริงในเดโม และไม่ควรต่อปั๊มจริงกับ firmware เวอร์ชันนี้
- ESP32 ใช้ HTTPS แบบไม่ตรวจใบรับรอง (`setInsecure()`) ผู้ที่ดักทราฟฟิกในวง Wi-Fi เดียวกันอาจเห็น `X-Device-Key` ได้ ยอมรับสำหรับต้นแบบ
- CORS อนุญาตเฉพาะโดเมนเว็บเดโม
- ข้อมูลที่ผู้ใช้ส่ง (บัญชี การแจ้งเหตุ) เป็นข้อมูลทดสอบ ผู้ดูแลระบบเห็นชื่อผู้ใช้ ที่อยู่ เบอร์โทร และพิกัดของรายการแจ้งเหตุ และอาจถูกลบเมื่อจบงาน ดู `privacy.html` และ `terms.html` ในเว็บ
- Railway และ Vercel ใช้แผนทดลอง/ฟรี อาจหยุดให้บริการเมื่อเครดิตหรือโควตาหมด
